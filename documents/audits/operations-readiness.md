## 復旧担当が行う手順

1. 障害の発生時刻と対象を記録し、外部からの要求と業務書込みを止める。バックアップ、障害時 DB、保存ファイルを別に保持する。稼働 DB に直接復元しない。
2. バックアップの取得時刻・ハッシュ・由来・復元先が新規の隔離 DB であることを確認する。実データの dump は現在の実装では秘密値を含み得るため、アクセスを担当者へ限定する。今回、実データの保管・暗号化・鍵復旧は試していない。
3. `pg_restore --exit-on-error` で隔離 DB へ復元し、スキーマ、件数、項目全体と添付の長さ・ハッシュを確認する。復旧前後の情報を記録する。
4. 外部接続を止めたまま、復元 DB の古い認証と共有権限を解除する。以下は本演習で実行した内容で、実環境では接続先を照合した担当者が行う。

   ```sql
   BEGIN;
   DELETE FROM sessions;
   DELETE FROM connect_tokens;
   DELETE FROM vault_memberships;
   UPDATE vault_invitations
      SET status = 'revoked', responded_at = NOW()
    WHERE status = 'pending';
   COMMIT;
   ```

5. 静的な Connect 認証値がある構成では、その値の有効化も止める。DB のセッション削除だけでは静的認証を無効にできない。設定値自体を問い合わせや証跡へ書かない。
6. 復元後の所有者・メンバーを現在の正当な利用者一覧と照合する。バックアップの共有権限を現在の承認と扱わない。確認済みの所有者から必要な権限を再登録し、退会済み利用者、解除済みメンバー、取消済み招待を復活させない。現在の本人確認と承認を証明できない間は外部アクセスを再開しない。
7. パスワード変更・退会・共有解除など、バックアップ以降の変更を現在の記録と突き合わせる。古いパスワードのハッシュも復元されるため、トークン削除だけで認証の問題が解消したと扱わない。最新の削除・変更を照合できない場合は復旧担当がアクセス停止を維持する。本人確認とパスワード復旧の実装は共有ToDo1174に依存する。
8. 架空利用者でアプリの読取・編集・添付・共有・失効を確認し、バックアップ後に失った更新と復旧時間を報告する。承認後に接続先を切り替え、停止中の更新も照合してから再開する。再開後の書込みを、古い DB の単純な復元で消さない。

ステップ4〜6は、未確認の共有をすべて閉じてから確認した権限を戻す手順である。バックアップの利用者・所有者がそのまま正しいという前提を置かない。追加の API 演習では、ステップ6の権限登録を架空 DB への SQL で模擬し、その後の認可を API で確認した。本人確認や本番の再承認手順、外部アクセス停止・再開と実クライアントの確認は未実施。
