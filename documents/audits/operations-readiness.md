# PassShare の復元演習と運用準備（2026-10-04）

架空データの PostgreSQL 復元演習は18項目が成功した。復元したデータを外部へ提供する前に、古い認証と共有権限を無効にし、現在の利用者を再確認する必要がある。販売前の運用要件 M8 は一部検証済みで、達成とは判定しない。

## 演習の対象と証拠

- 基準ソース: `6525462471191fe917a00c28e6256843bfb7a747`。
- 使用したスキーマ: `backend/src/db/schema.js` と `backend/src/db/auth-schema.js` の SQL をそのまま適用した。
- PostgreSQL 16.14。イメージの digest は [実測記録](evidence/1177-restore-drill.json) に固定した。
- 架空の利用者2人、パスワードボックス1個、項目2件、バイナリ添付1件、共有権限2件、招待1件、セッション1件、接続トークン1件、ログイン失敗1件、要求記録1件。
- メールは `example.invalid`、IP は `192.0.2.1`。項目、認証のハッシュ、添付はすべて架空。実ユーザーの DB と秘密設定を取得していない。
- 自分のコンテナだけを使用。ネットワークは `none`、公開ポートなし、CPU 1・メモリ512 MiB。演習後にコンテナとその専用ボリュームを削除した。
- `pg_dump -Fc` で取得し、新規の別 DB へ `pg_restore --exit-on-error`。全10テーブルの行を JSONB として正規化し、順序を固定して全文比較した。
- 補助処理と架空 dump は `D:/CC/Work/passshare-orch-20261004-202220/` に保持。PowerShell は今回の単発調査用で、製品の定期処理へ追加していない。

## 確認した結果

| 確認 | 結果と範囲 |
|---|---|
| 内容の復元 | 全10テーブルが取得前と全文一致。追加フィールド、日本語、複数URL、項目の版、添付4バイトを保持 |
| 取得後の更新 | バックアップ後に追加した項目1件は復元されない。現在 DB を巻き戻すとその後の更新を失う |
| 削除の取消 | 復元 DB でパスワードボックスを削除し ROLLBACK。連動する項目・添付・共有も元の全文へ戻った |
| 整合性 | 存在しないボックスへの共有登録は外部キーで拒否 |
| DB の読取専用権限 | SELECT は成功、DELETE は拒否。アプリのメンバー権限を検証した結果とは区別する |
| 古い認証 | dump のセッション1件と接続トークン1件が復元されることを確認。復元 DB だけで両方を削除し、未承諾招待を取消 |
| 古い共有権限 | dump 取得後に除名したメンバーが復元 DB に戻ることを再現。復元 DB の共有権限をすべて解除し、架空の確認済み所有者だけを再登録。除名したメンバーは再登録されない |
| データと原 DB の保持 | 認証・共有解除後も項目2件と添付1件を保持。復元・解除の操作で原 DB の内容は変わらない |
| 再起動 | PostgreSQL を再起動して、復元と認証・権限整理後の全文が一致 |

最初の試行は、補助処理が空のポート一覧を誤判定して停止した。コンテナを回収し、配列長を明示する修正後に16項目が成功した。共有権限の巻き戻りを追加した最終試行が18項目成功。最初の補助処理の失敗を、製品の不具合や成功した試行として扱わない。

## 時間と失う更新の範囲

| 測定 | 実測 |
|---|---|
| dump 取得 | 182.2488 ms |
| 新規 DB 作成から復元・全テーブル比較完了 | 520.1229 ms |
| 比較完了時のバックアップの古さ | 1.1125518秒 |
| dump サイズ | 22,297バイト |
| 取得後に失われた更新 | 項目の追加1件。共有解除も巻き戻った |

520 ms はこの小さい架空 DB の「復元と内容検査」の所要時間である。認証・権限の再確認、接続先切替、アプリ確認を含むサービスの RTO ではない。取得後の項目1件を失う実験でスナップショットの範囲を確認したが、本番の RPO、バックアップ頻度、PITR 利用可否は未測定。顧客にこれらの時間や無損失の復旧を約束しない。

## 復旧担当が行う手順

1. 障害の発生時刻と対象を記録し、外部からの要求と業務書込みを止める。バックアップ、障害時 DB、保存ファイルを別に保持する。稼働 DB に直接復元しない。
2. バックアップの取得時刻・ハッシュ・由来・復元先が新規の隔離 DB であることを確認する。実データの dump は現在の実装では秘密値を含み得るため、アクセスを担当者へ限定する。今回、実データの保管・暗号化・鍵復旧は試していない。
3. `pg_restore --exit-on-error` で隔離 DB へ復元し、スキーマ、件数、項目全体と添付の長さ・ハッシュを確認する。復旧前後の情報を記録する。
4. 外部接続を止めたまま、復元 DB の古い認証と共有権限を解除する。以下は本演習で実行した内容で、実環境では接続先を照合した担当者が行う。

   ```sql
   BEGIN;
   DELETE FROM sessions;
   DELETE FROM connect_tokens;
   DELETE FROM vault_memberships;
   UPDATE vault_invitations
      SET status = 'revoked', responded_at = NOW()
    WHERE status = 'pending';
   COMMIT;
   ```

5. 静的な Connect 認証値がある構成では、その値の有効化も止める。DB のセッション削除だけでは静的認証を無効にできない。設定値自体を問い合わせや証跡へ書かない。
6. 復元後の所有者・メンバーを現在の正当な利用者一覧と照合する。バックアップの共有権限を現在の承認と扱わない。確認済みの所有者から必要な権限を再登録し、退会済み利用者、解除済みメンバー、取消済み招待を復活させない。現在の本人確認と承認を証明できない間は外部アクセスを再開しない。
7. パスワード変更・退会・共有解除など、バックアップ以降の変更を現在の記録と突き合わせる。古いパスワードのハッシュも復元されるため、トークン削除だけで認証の問題が解消したと扱わない。最新の削除・変更を照合できない場合は復旧担当がアクセス停止を維持する。本人確認とパスワード復旧の実装は共有ToDo1174に依存する。
8. 架空利用者でアプリの読取・編集・添付・共有・失効を確認し、バックアップ後に失った更新と復旧時間を報告する。承認後に接続先を切り替え、停止中の更新も照合してから再開する。再開後の書込みを、古い DB の単純な復元で消さない。

ステップ4〜6は、未確認の共有をすべて閉じてから確認した権限を戻す手順である。バックアップの利用者・所有者がそのまま正しいという前提を置かない。ステップ5〜8と実アプリの外部アクセス停止・再開は今回未実施。
