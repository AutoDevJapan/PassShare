## 招待の本人確認

任意のメールアドレスで登録した人が、一覧に出た招待を承諾すると共有に参加できた。
メールアドレスを知ることは、本人の証明にならない。

Rust の共通判定は、招待先アカウント、未応答状態、期限、招待した所有者の現在の権限、
独立した経路で受け取った確認コードをすべて要求する。
コードは既存の乱数生成器による256bitの値で、所有者への作成応答に一度だけ返す。
DB は SHA-256 の照合値だけを保持する。招待一覧やエラー応答にコードを返さない。

所有者は、普段から使う社内の連絡先、対面、本人確認済みの通話などを通してコードを渡す。
参加希望者が入力した連絡先に、そのまま送り返してはならない。
この方式は管理者が確認した人への参加許可であり、全アカウントのメール所有確認ではない。

API 手順:

1. 所有者が `POST /api/auth/vaults/{id}/invitations` にメールアドレスを送る。
   応答の `confirmationCode` を本人へ確認済みの別経路で伝える。
2. 本人がログインし、`POST /api/auth/invitations/{id}/accept` に
   `{"confirmationCode":"受け取ったコード"}` を送る。
3. コードのない旧招待は拒否される。所有者が取消し、改めて招待する。
   作成応答を失った場合も取消して作り直す。URL・ログ・問い合わせ本文にコードを置かない。

## 取消と除名

PostgreSQL はボックスの行、次に招待の行をロックし、状態を読んだ後に Rust で判定する。
期限は書き込み直前にも確認する。所属作成と招待消費は同じ接続・同じ取引で確定する。
取消が先に確定した場合は参加を拒否する。承諾が先に確定した場合は招待を消費済みとし、
退出には所属削除を使う。競合の両操作が成功したと誤認させない。

所属削除と既存 Connect 認証情報の取消も同じ取引で確定する。
すべてのユーザー向け Connect リクエストで、発行時の範囲と現在の所属の共通部分を使う。
古い認証情報の復元や並行発行で所属の権限が復活することを防ぐ。
既存のサーバー管理者向け互換認証の提供環境と制約は別途保持する。
