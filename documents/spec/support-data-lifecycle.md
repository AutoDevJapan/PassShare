# 問い合わせ・解約とデータの保管契約

> 共有ToDo1177 / 親1197、2026-10-05
> 状態: 技術側の運用案。受付サービス、本人確認、退会、保持設定と顧客契約は未完成。

問い合わせの受付、アカウント退会、チーム契約の解約、データの取り出しと削除は別の処理として管理する。顧客が確認できる受付番号と処理状況を用意し、バックアップ復元でも確定した退会・削除・共有取消を戻さない。[復元演習](../audits/operations-readiness.md)と[運用入口](../runbooks/operations.md)を参照する。

## 役割と受付経路

| 役割 | 行える処理 | 確認する根拠 |
|---|---|---|
| 本人 | 自分の問い合わせ、データ取得・退会要求 | 現在の本人確認。メール文字列や古いセッションだけでは代用しない |
| ボックス所有者 | 共同データの移管、メンバー変更、認められた出力 | 対象ボックスの現在の権限と移管先の確認 |
| 契約上の管理者 | 席数・契約変更、解約の申請 | 顧客契約の管理権限。ボックス内容の閲覧権限を自動で与えない |
| 運用担当者 | 受付、影響調査、隔離復元、処理結果の記録 | 受付番号と承認された作業範囲。申請者へ秘密値を求めない |

リポジトリの問い合わせ・法務文書には、動作確認済みの顧客窓口 URL やメールアドレスが定義されていない。内部 Discord と GitHub の Issue を、契約済みの顧客窓口として流用しない。窓口の選定・受付担当・受付時間・一次返信の約束は、公開前に確定する。技術側は架空の問い合わせが受付から担当者へ届き、顧客へ同じ受付番号を返せることを実経路で検証する。

受付に記録する項目は、受付番号、申請種別、本人確認の状態、対象契約とボックスの識別子、製品版・OS、発生時刻とタイムゾーン、匿名のエラー分類、影響範囲、担当者、処理状況、次の連絡予定、処理結果である。データそのものは要求しない。パスワード、マスターパスワード、復号鍵、認証値、項目本文、DB dump を本文や添付として収集しない。

## 処理状況と完了条件

| 状況 | 次へ進む条件 | 失敗した場合 |
|---|---|---|
| 受付済み | 同一の受付番号を返し、担当者が内容を読める | 受付の保存・返却を確認し再開。同じ要求の再送で重複実行しない |
| 確認中 | 本人・契約管理・ボックス権限を操作ごとに確認 | 要求を保持し、権限のない出力や削除を行わない |
| 処理準備済み | 移管先の承認、完全な取得、実行する削除範囲・日時を確認 | 取得不完全や移管不能を説明し、その要求の処理を保留 |
| 処理中 | 操作の識別子と結果を保存し、失効・移管・削除を照合 | 応答切断でも結果を照会。無条件の再実行をしない |
| 処理済み | アプリの結果と受付記録を照合し、要求者が確認できる | 不一致を未完として保持。受付文の返信だけで完了にしない |

申請者からの取消は不可逆の削除前に扱う。削除が始まった後は、現在の実行結果を確認し、取消によって削除済みデータが復元されるとは約束しない。本文訂正と新しい申請も識別して記録する。

## 解約・退会の実行順序

1. 契約の終了、席の削除、個人アカウントの退会、ボックス削除のどれを求めるか受付で分ける。課金の終了だけでアカウントや共同データを削除しない。
2. 本人と各操作の権限を現在の記録で確認する。最後のボックス所有者が退会する場合は、承諾された所有者移管または確認済みのボックス削除を先に完了する。
3. 所有する端末ファイルとクラウドデータを分ける。クラウド出力は項目全体、非表示フィールド、複数URL、添付、版と必要な鍵の保持を確認し、別環境で読めることを確認する。CSV 単独の出力を完全取得としない。共有先に権限がないデータを含めない。
4. 対象のセッション、接続トークン、招待、共有、端末資格を失効する。現在の資格を使う読取・保存経路で拒否を確認し、別ボックスや他の利用者の操作が継続することも確認する。
5. 確認したデータ範囲だけを削除する。最新の削除・失効・移管の記録は、同じ復元で巻き戻らない保全先にも保持する。保存に失敗した場合は、復元後の再開を許可しない。具体的な保全先と処理の実装は1174/1175との統合が必要。
6. バックアップ・ログ・受付記録に残るものと、その消える条件を分けて説明する。バックアップ全体を1人の退会に合わせて消し、他の利用者の復元能力を失わせない。
7. 課金側で終了日時、最終請求、席変更、返金の適用結果を照合する。現行の料金基準だけではこれらの条件は定まらない。
8. 元の受付番号へ処理した範囲、完了時刻、未処理の範囲と理由を返す。データの秘密値は返さない。

## 保管対象と未確定の期間

期間はこの仕様で独自に決めない。技術側は対象別の取得・削除・復元時の扱いを検証して、契約する期間と実設定を一致させる。

| 対象 | 保持を始める時点と終了条件 | 現在の確認状況 |
|---|---|---|
| 端末の `.pbox` とコピー | 利用者が保存・削除する。サービス側の退会で端末ファイルを自動削除しない | 実端末での取得・復旧は1176で継続 |
| クラウドのアカウントと資格 | 登録から確認済みの退会・失効処理まで。DB とアプリの両方で拒否を確認 | 正式な本人確認・退会経路は1174で未完 |
| 個人・共同の項目と添付 | 所有・共有・移管を確認した削除範囲に従う | 完全出力と鍵の扱いは1175/1176に依存 |
| DB バックアップとPITR履歴 | 取得から実際の保持窓が終了するまで。削除済み情報を復元時に利用可能へ戻さない | Railway の実設定・最古/最新復元可能時刻は未確認 |
| 最新の退会・共有取消・削除記録 | 処理確定後、当該状態を戻し得るバックアップがなくなり復元経路を閉じたことを確認するまで | 別保全先と復元への反映は未実装。ここで無期限保存を承認しない |
| 問い合わせと最小の操作記録 | 受付から処理・確認まで。終了後の保持期間を契約・目的に合わせ確定 | 受付経路、閲覧権限、設定と削除検証は未完 |
| 演習の dump と診断出力 | 演習の確認と必要な証拠保全を終えたら回収。秘密値を新しい一般公開資料へ保存しない | 架空演習の旧資料は履歴として保持。新しい認証入り dump は生成物として外へ残さない |

バックアップの保持日数は、解約後に顧客が取得できる日数や、問い合わせ本文の保管日数と同じではない。設定変更で保持窓が延びたら、退会・取消記録を早く捨てて復元で復活させないため、再度照合する。
