# パスワードボックスの端末内復旧画面 — 受入検査

ToDo1163の復旧画面は、端末上の既存 `.pbox` を復旧コードで読み、利用者が指定した新しいマスターパスワードで保存する。パスワード変更では復旧コードをローテーションしない。同じコードは、明示的にローテーションするまで再利用できる。

## Linuxの実際のデスクトップ画面で確認する範囲

`crates/passshare-core/examples/webview_acceptance.rs` の `desktop local-recovery` は、既存の tauri-driver / WebKitGTK / Xvfb による有限の受入検査である。CSPを適用したTauriアプリのビルド後に `.github/workflows/native-webview.yml` から実行する。実際の `SetupPanel` の `data-testid="recover-password-box"` をクリックし、`LocalRecoveryPanel` の入力と送信ボタンを操作する。復旧コマンドを検査側から直接呼んでフォームの代わりにすることはない。通常の解除操作は `data-testid="open-password-box"` を使い、ボタンの表示順に依存しない。

1. 実際の作成IPCで合成 `.pbox` と復旧コードを生成し、項目追加IPCでURL・ユーザー名・パスワード・メモ・タグ・お気に入りを含むログイン項目と、本文付きのメモを保存する。生成されたIDだけを取得結果から使い、それ以外の全フィールドは投入値から組み立てた独立の期待DTOと照合する。全画面DTOと復号した全保存内容を比較用に保持し、ロックする。
2. 別の復旧フォームにパス・コード・新パスワード・確認を入力してキャンセルする。フォームとコード表示が消え、解除画面の入力が空になり、取り外された秘密入力の参照も空になることを確認する。元ファイルの全バイトとSHA-256が一致し、ネイティブ状態もロックのままであることを確認する。
3. フォームを開き直し、確認入力だけ異なる値で送信する。実際の画面にエラーが表示され、項目が表示されず、元ファイルの全バイトとSHA-256が一致し、秘密読み取りも拒否されることを確認する。
4. 確認入力を直して送信する。元の項目が実際の画面に現れ、フォームが取り外された後の描画とネイティブ往復が済んでも解除状態が続き、全画面DTOが一致することを確認する。
5. 同じ元ファイルを新パスワードで開き、全保存内容が一致し、暗号化ファイルが更新されたことを確認する。その存在と新パスワードでの認証成功を前提に、旧パスワードが認証エラーになることを確認する。同じ復旧コードでの読み取り復旧も全項目が一致し、ファイルを変更しないことを確認する。
6. 再ロック後、実際の通常解除画面から新パスワードで開き直し、全画面DTOを比較する。旧パスワードによるネイティブ解除は拒否される。最後にロックし、認証確認によってファイルが変わっていないことを確認する。

旧・新・確認不一致用・項目用のパスワードは、それぞれ独立したOS乱数から生成する。復旧コードは実際の作成結果を使う。秘密文字列と復号バイト列には可能な範囲で消去ガードを付け、失敗時には固定の検査名だけを出す。JSON証拠は真偽値と件数のみを保存する。スクリーンショットはキャンセル後の空の合成解除画面だけを保存し、コード入力画面は撮影しない。

モード全体には既存の120秒の絶対期限を使う。既存のUnixプロセスグループ終了処理、CSP検査、通常の5分アイドルロック検査は維持する。

## この検査から主張しない範囲

Linuxの実際のデスクトップレンダラーでのフォーム操作を確認する検査であり、Android実機・スマートフォンのバックグラウンド遷移・実機でのファイル選択を確認した証拠ではない。オーナーのChromeでのファイル選択の制約とも別の検査基盤である。

Windowsでは関連exampleのテストとClippyを確認できる。意味を検査するテストは実在する合成ファイルにログイン項目と本文付きメモを保存し、全項目と全保存内容の維持、正しい新パスワードによる認証、旧パスワードの認証拒否、コード再利用、読み取り時のファイル維持を確認する。ファイルが無い場合は不変と判定せずエラーとし、件数だけ同じでもフィールドが変われば比較が失敗することも確認する。実レンダラーの成功はLinux CIの実行結果を確認した時点で報告する。
