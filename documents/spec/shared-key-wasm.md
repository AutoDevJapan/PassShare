# 共有鍵のWASMバインディング

既存Coreのアカウント鍵と共有鍵を、JavaScriptから不透明なハンドルで操作する境界です。
[Core仕様](shared-key-crypto.md)の暗号処理・形式・信頼条件をそのまま使います。
この変更はM4の一部であり、M4全体や本番導入の完了を示しません。

実装は `packages/cloud-wasm/src/shared.rs`、公開する型は `CloudAccountIdentity` と
既存の `CloudPasswordBox` です。秘密の鍵を文字列やJSONとして入出力するAPIはありません。
Core・依存関係・所有者用の既存形式・Workerのプロトコルは変更しません。

## アカウント鍵の公開API

以下はJavaScriptから見た名前です。`unlock` は静的メソッドです。

| 呼び出し | 結果 |
|---|---|
| `new CloudAccountIdentity(accountContextJSON)` | Coreで鍵を生成し、ハンドル内の `Option<AccountIdentity>` に保持します。 |
| `identity.publicIdentity()` | Coreの公開記述子を固定順のJSONで返します。ロック後は拒否します。 |
| `identity.wrap(password)` | 暗号化したアカウント鍵のバンドルJSONを返します。 |
| `CloudAccountIdentity.unlock(bundleJSON, password, independentlyHeldAccountContextJSON, expectedKeyId)` | 独立して保持する文脈と公開鍵の指紋を検証し、ハンドルを復元します。 |
| `identity.lock()` | 保持する鍵を破棄します。繰り返し呼べます。 |

アカウント文脈は `{accountId, identityVersion}` です。nilのUUIDは拒否し、版は
1〜9007199254740991に制限します。公開記述子の形とフィールド順は
`{accountId, identityVersion, publicKey, keyId}` です。
`publicKey` は32バイトのcanonicalな標準Base64、`keyId` は小文字16進64桁の指紋です。
ハンドルに秘密のgetter・鍵導出の公開API・Clone・Debug・serdeはありません。

保存バンドルは `{format:1, salt, wrapped}` です。
`wrapped` はCoreの `{format:1, context, nonce, ciphertext}` をそのまま使います。
ソルトは16バイト、nonceは24バイト、暗号文は48バイトです。
各値はcanonicalな標準Base64であり、空白、余分な文字、異なる長さ、非canonicalな表現は拒否します。
外側・内側の形式はともに1だけを受け付けます。すべての階層で未知フィールドを拒否します。

バンドルのソルトを用いて、既存の `derive_root` を呼びます。
形式1の導出は **Argon2id、64MiB、3回、並列度4** に固定します。
パスワードの条件は既存所有者バンドルと共通です。入力のUTF-8長を1024バイト以下に制限し、
NFCで正規化した後に8文字以上であることを確認します。
Coreのアカウント鍵専用AADで包み、独自の暗号方式を追加しません。

復元するアカウント文脈と `expectedKeyId` は、バンドルや同時に取得したサーバー応答から
コピーしてはいけません。呼び出し側が別に保持し、信頼した値を渡します。
同じアカウント・版で生成した別のアカウント鍵への差し替えも、固定した指紋で拒否します。

## パスワードボックスの共有API

| 呼び出し | 結果 |
|---|---|
| `box.wrapForRecipient(senderIdentity, trustedRecipientPublicJSON, independentlyHeldSharedKeyContextJSON)` | CoreのAuth HPKEで鍵を包み、共有エンベロープJSONを返します。 |
| `CloudPasswordBox.unlockForRecipient(envelopeJSON, recipientIdentity, trustedSenderPublicJSON, expectedSharedKeyContextJSON)` | Coreで検証・復号し、受信者を現在の呼び出し側とするハンドルを返します。 |

共有文脈の全フィールドが必須です。形は
`{passwordBoxId, senderAccountId, recipientAccountId, keyEpoch, senderIdentityVersion,
recipientIdentityVersion, senderKeyId, recipientKeyId}` です。
エンベロープの形・suite・Auth HPKEの条件はCore仕様と同じです。

送り手は、現在のハンドルの呼び出し側アカウントと一致しなければなりません。
共有文脈のボックスID・鍵世代もハンドルと照合します。
Coreが送り手・受け手の実際のアカウント・版・公開鍵の指紋を全フィールドと照合します。
受信時は、信頼した送り手の公開記述子と、独立して保持する期待文脈を明示的に渡します。
期待値を受信エンベロープから導きません。

受信ハンドルのスコープは、独立した期待文脈のボックスID・鍵世代と、実際の受信者の
アカウントから構成します。送り手を受信者の所有者として代入しません。
既存の内部フィールド `Session.owner` は、この経路では**現在の呼び出し側とボックスと鍵世代**を
束縛するための値です。サーバー上の実際の所有者を示すものではありません。
既存の項目の暗号化・復号・ロックは同じスコープに従います。
項目全体を扱うため、配列・添付メタデータ・未知の項目フィールドも保持します。
既存DTOにある `vault` というフィールド名は互換性のためそのまま扱います。

受信経路で生成したハンドルは `wrap_for_owner` を拒否します。
所有者として生成・復元した従来のハンドルは、従来どおり所有者用バンドルを出力できます。
受信者が再共有する場合も、送り手はその受信者自身であることを照合します。
これは暗号上の操作だけであり、再共有する製品上の権限を付与する機能ではありません。

## 信頼と権限の境界

公開記述子がサーバーに載っていることや、鍵を持っていることだけでは、信頼・所有権・
メンバー権限を認めません。公開鍵の固定や帯域外の指紋確認、期待するアカウント・版・
ボックス・最新の鍵世代の選択は呼び出し側の責任です。
構造が正しい公開鍵と、本人の鍵として信頼できる公開鍵は区別します。
将来のAPI・サーバー側で、確認済みのメンバー関係と権限に基づいて保存・配布を認可する必要があります。
このバインディングはその認可を実装せず、確認済みのメンバー関係を自動的に主張しません。

Core仕様に記載されたAuth HPKEのKCI・前方秘匿性・再送の制限はそのまま残ります。
鍵や平文が既に渡った受信者から、その内容を取り消すことはできません。

## 入力上限・エラー・秘密の破棄

| 入力JSON | UTF-8バイト上限 |
|---|---:|
| アカウント文脈 | 256 |
| 信頼済み公開記述子 | 512 |
| 共有鍵文脈 | 1024 |
| アカウント鍵バンドル・共有エンベロープ | 2048 |

パース失敗・認証失敗・改ざん・文脈不一致・指紋不一致はすべて固定の
`PS051: Invalid encrypted data` を返します。入力値や下位ライブラリのエラーは返しません。
ロックしたアカウント鍵は `PS057: Account identity is locked`、ロックしたパスワードボックスは
既存の `PS057: Password box is locked` です。受信ハンドルの所有者用出力もPS051です。

Rust側のパスワードは既存の `Zeroizing` を使います。アカウント鍵と復元時の平文バッファの
消去は既存Coreの処理に委ねます。WASMメモリ全体の消去を保証しません。
JavaScriptから渡すパスワードや項目の文字列、および復号結果は平文です。
JavaScriptの文字列・バッファ・UI状態の消去をこの境界で保証することはできません。
アカウント鍵をロックしても、既に開いた別のパスワードボックスは自動的にはロックされません。
それぞれのハンドルをロックまたは破棄する必要があります。

## 検証と残作業

追加した `packages/cloud-wasm/tests/shared_api.rs` は、wasm32の
`wasm_bindgen_test` を使い、Nodeの標準ランナーで公開バインディングを呼ぶテストです。
Coreだけを直接呼ぶ既存テストは残します。

追加テストの対象は、A・B・Cの保存と復元、NFCとパスワードの境界、同じ文脈の別鍵への差し替え、
誤ったパスワード・独立した期待文脈・指紋、未知フィールド、長さ・Base64・改ざん、ロック、
A→Bの共有と項目全体の往復、Cの拒否、送り手・受け手・世代・ボックス・版・指紋の変更、
受信者による所有者用バンドル出力の拒否、受信者を送り手とする再共有の束縛です。

2026-10-10にnative11件・Clippy・doc（0例）が成功しました。Nodeで動く新しいWASMテスト5件と、既存の公開境界2件・Core共有鍵1件も成功しました。別モデルが指摘した拒否テストを修復し、項目と期待文脈を同じ別ボックスへそろえて、正当なハンドルでは成功し、元の受信ハンドルでは拒否することを再確認しました。

releaseモジュールから生成したJavaScriptを、既存のRust受入exampleから実際に呼び出す検査も成功しました。アカウント鍵の生成・公開指紋・保存・ロック・独立した指紋による復元、A→Bの共有と全DTOの復号、Cの拒否、受信者の所有者用出力拒否、鍵とボックスのロックをRustが照合します。以前のformat 1とNFCのベクトル検査も維持しています。Rustのテストから公開メソッドを呼ぶ結果と、生成されたJavaScriptのABIを呼ぶ結果は別々に確認しました。追加差分を含む別モデルの確認は全指摘0件です。候補CIと統合後mainは別途確認します。

Web配布用のJavaScriptとWASMも生成し直しました。ソースの指紋には新しい `src/shared.rs` を含む32入力を記録し、3配布ファイルのハッシュを検査します。Webのビルドは成功しました。

GitHubのCloud WASM実行37996557828（ソース `bbbfd6ca75cd046df6423b22839dc28c6dbe23ed`）が成功した後、リポジトリ・ブランチ・実行元・ワークフローと32入力の一致を確認して成果物を取得しました。PCで生成したものとはバイトが異なったため、配布ファイルをCIの成果物へ置き換えました。WASMは616820バイト、SHA-256は `694a46dae393b80791b11a9c9ea48450186a598fdb8e8b42b839d5764e8fb469` です。取得した同じバイトをハッシュ検査して配布先へ書き込み、ブラウザ用の実JavaScriptとWASMをNodeのESモジュールとして直接読み込む検査も成功しました。生成済みWASMを再加工した検査は実行ファイル名の誤りで失敗し、証拠には数えず、元のWeb成果物の検査へ切り替えました。

生成元のメタデータも、以前のCI番号から今回の実際のソース・実行番号へ更新しました。追加したWeb成果物の直接検査はCIにも接続しました。最新の候補CIと統合後mainは確認中です。Workerのメッセージ形式や画面の操作は、この共有APIへまだ接続していません。

M4に残る作業は、各クライアントへの接続、鍵の登録と信頼の確認、保存と配布、メンバー認可、
失効と世代更新、項目の再暗号化、復旧、移行です。
今回のフロントエンド変更は、配布バインディングと指紋の更新です。画面・画像・API・RootCoreの変更は含みません。
