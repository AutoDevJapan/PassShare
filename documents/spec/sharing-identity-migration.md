# 旧共有記録の本人確認

共有ToDo #1163 / #1174、M3。PR607で新しい招待の確認コードを強制した後も、
以前の共有記録には本人を確認した証拠がない。参加済みという状態だけを証拠にしない。

Rustの共有スキーマは所属へ `confirmed_at` を追加し、現在のアクセス判定を定義する。
ボックスを作成した所有者はその所有権を保持する。
通常メンバーはコードを照合した承諾取引でだけ確認済みになる。
古い招待の承諾済み状態や、作成時の確認コードのハッシュから、自動で確認済みにしない。
新旧サーバーが混在した期間の承諾でも、コードを使ったとは限らないためである。

所属・項目・添付は削除しない。未確認の通常メンバーは共有を読めなくなる。
所有者のメンバー一覧に「本人確認待ち」を表示し、同じアカウントへ新しいコードで招待できる。
本人がコードを使うと同じ所属を確認済みに更新し、元のボックスと項目・添付を再び使える。
所有者・通常メンバーを料金の管理者・通常メンバーへ自動換算しない。

Connect認証情報の新規発行、現在の所属照合、共有API、原子保存の取引も、同じ判定を使う。
保存中の確認状態の変更は所属の共有行ロックで直列化する。
原子保存で新しく作るボックスの所有者の扱いも、通常のボックス作成と一致させる。

受入: 架空メンバーを未確認へ戻し、スキーマを再適用しても再承認されないことを確認する。
有効な旧認証情報で項目・添付の読み取りを拒否し、コードなしの再承諾も拒否する。
所有者が再招待し、正しいコードで参加した後、同じ項目と添付の実バイトが保持されることを確認する。
当該試験はPostgreSQLの正式APIで実行する。成功は結果を得てから記録する。

配備時は旧バージョンのサーバーを終了し、全要求がこの判定を通ることを確認する。
復元では過去の確認記録を現在の承認と扱わず、外部からの利用を閉じて所属・旧認証を解除する既存手順を維持する。
配備・全クライアント・本番復元の受入を、スキーマの実装だけで完了としない。
